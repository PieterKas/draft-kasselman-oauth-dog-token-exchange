Delegated Operation Grant Issuance using Token Exchange and Workload Authorization Grants

Abstract

The OAuth 2.0 Delegated Operation Grant (DOG) is a JSON Web Token (JWT) authorization grant that authorizes specific operations at a protected resource. An intermediary, such as a platform or credential manager, holds the DOG and does not disclose it to the workload or agent that performs the operations. This document specifies how the intermediary obtains, presents, and uses a DOG on behalf of a workload or agent that acts either on its own behalf or on behalf of a user. The intermediary can exchange the DOG for an OAuth access token or present it directly to a resource server that is not protected by an OAuth authorization server.¶

1. Introduction

The OAuth 2.0 Delegated Operation Grant (DOG) [DOG] is a JWT used as an authorization grant, as described in Section 2.1 of [RFC7523]. An intermediary, such as a platform or credential manager, holds the DOG and uses it to obtain access for a workload or agent that runs in a less trusted environment. The workload or agent performs the authorized operations but never receives the DOG itself.¶

This document defines:¶

  • The DOG format: A DOG is a signed JWT with the typ header value oauth-dog+jwt. It names one resource authorization server (aud) and one protected resource (resource), lists the authorized operations (scope), and binds the grant to a key (cnf).¶

  • Requesting a DOG: The intermediary requests a DOG using OAuth 2.0 Token Exchange [RFC8693]. It presents a Workload Authorization Grant (WAG) [I-D.carleton-workload-authz-grant] that identifies the workload or agent. When the workload or agent acts on behalf of a user, the request also includes a subject token that identifies the user.¶

  • User Interaction: When the authorization server requires user interaction, it uses a Deferred Token Response [I-D.ietf-oauth-deferred-token-response]. The user authenticates and consents at an interaction URI while the intermediary polls for the result. When no interaction is required, the authorization server issues the DOG immediately.¶

  • DOG Presentation: The intermediary presents the DOG to a resource authorization server as a JWT authorization grant [RFC7523] and receives an access token. It can also present the DOG directly to a resource server that is not protected by an OAuth authorization server, which returns a session cookie.¶

  • Access Credential Use: The intermediary delivers the resulting access token or cookie to the workload or agent, or injects it into the requests that the workload or agent makes.¶

3. Overview

3.1. Phase 1: Obtaining a DOG

In the first phase, the platform obtains a DOG from the authorization server on behalf of an agent. The platform presents a WAG that identifies the agent and, when the agent acts on behalf of a user, a subject_token that identifies the user. The authorization server either issues the DOG immediately or defers the request until it can decide, which may require the user to authenticate and consent. In both cases, the DOG is bound to a key that the platform generates for that DOG and never discloses. The agent receives neither the DOG nor its key. Figure 1 shows the flow.¶

  1. The platform issues a Workload Authorization Grant (WAG) that identifies the agent (sub claim). The WAG can also carry information about the device or hardware and the issuance policy that the platform applied.¶

  2. The platform sends a token exchange request [RFC8693] to the authorization server. The request includes the WAG and names one protected resource and the requested operations. When the agent acts on behalf of a user, the request also includes a subject_token (e.g. an ID token or refresh token) that identifies the user. The request includes the completion_mode parameter with the values "deferred" and "deferred_interactive" [I-D.ietf-oauth-deferred-token-response], and carries a DPoP proof [RFC9449] for the a key associated with the DOG (DOG key). A DOG key may be ephemeral, unique per DOG and scoped to a workload or agent, depending on implementation choices and the risk profile of the deployment.¶

    The authorization server then follows either step 3 or steps 4 to 8.¶

  3. If the authorization server can decide synchronously, it issues the DOG in the token exchange response. The DOG is bound to the Dog key. Go to Step 9.¶

  4. Otherwise, the authorization server returns a deferred response with a deferral_code bound to the DOG key. Its error code indicates whether the platform must direct the user to an interaction_uri (interaction_required), the authorization server contacts the user itself (interaction_pending), or the decision does not involve the user (authorization_pending).¶

  5. If the error code is interaction_required, the platform directs the user to the interaction_uri.¶

  6. If the user is involved, the user authenticates, if required, and agrees to the requested operations.¶

  7. The platform polls the token endpoint with the deferral code until the request completes. Each poll carries a DPoP proof for the same DOG key.¶

  8. When the request completes, the authorization server issues the DOG in the response to a poll.¶

  9. The platform stores the DOG and the DOG key. It does not disclose the DOG or the DOG key to the agent.¶

3.2. Phase 2: Using a DOG

In the second phase, the agent sends its requests for a protected resource to the platform, and the platform uses the DOG to obtain access and forwards each request. If the resource is protected by an OAuth authorization server, the platform exchanges the DOG for an access token. If the resource is a web server that is not protected by OAuth, the platform presents the DOG directly and receives a session cookie. In both cases, the platform proves possession of the DOG key and adds the resulting credential to the requests it forwards. The agent never receives a DOG, a key, an access token, or a cookie. Figure 2 shows the flow.¶

  1. The agent sends a request for a protected resource to the platform. The platform selects the DOG for that agent and resource.¶

    The platform then follows either steps 2 to 5 or steps 6 to 9.¶

  2. If the resource is protected by an OAuth authorization server and the platform holds no valid access token for that resource server, the platform presents the DOG to the resource authorization server named in the DOG, using the jwt-dpop grant type [I-D.parecki-oauth-jwt-dpop-grant] with a DPoP proof [RFC9449] signed with the DOG key.¶

  3. The resource authorization server validates the DOG and the DPoP proof and issues an access token that identifies the agent and is bound to the DOG key. The platform caches the access token for later requests under the same DOG.¶

  4. The platform forwards the agent's request to the resource server with the access token and a new DPoP proof signed with the DOG key.¶

  5. The resource server validates the access token and the DPoP proof and returns a response to the platform. Go to step 10.¶

  6. If the resource is a web server that is not protected by OAuth and the platform holds no valid session for the DOG, the platform presents the DOG directly to the web server with a DPoP proof signed with the DOG key.¶

  7. The web server validates the DOG and the DPoP proof and returns a session cookie. The platform keeps the cookie for later requests under the same DOG.¶

  8. The platform forwards the agent's request to the web server with the session cookie.¶

  9. The web server returns a response to the platform.¶

  10. The platform returns the response to the agent.¶
